# Підключення CMS API до Vortex

Стан: 18.11.2026. Реалізація підготовлена за [відповіддю PHP-розробника](cms-developer-reply-2026-11-18.md) та [мапінгом полів](field-mapping.md). Архів `docs/cms-handoff/2026-11-18` залишається незмінним знімком переданого контенту.

## Середовища та запуск

Налаштовуються на **Node-сервері**, не у браузерній збірці:

- test: `CMS_API_BASE_URL=http://site-api.dev.vortex-services.com/api`;
- production: `CMS_API_BASE_URL=https://site-api.director.vortex-services.com/api`;
- `BLOG_API_BASE_URL` можна не задавати, якщо блог має той самий API-корінь; окреме значення має пріоритет;
- корінь — без `/blog`;
- для production вимкнути демонстраційний блог: `BLOG_DEMO_MODE=false`, `VITE_BLOG_DEMO_MODE=false`.

Робочий `.env` автоматично не змінено. За повідомленням CMS-розробника test-хост ще повертає HTML 404; немає живих fixtures, імпорту та підтвердженої production-доступності. Увімкнення непрацездатного CMS зупинило б сайт із 503. Після запуску PHP API потрібно імпортувати переданий контент та провести перевірки нижче. Тести в репозиторії використовують ізольовані змодельовані відповіді, а не видають їх за живий CMS.

## Опублікований контент

`GET /api/content` на сайті лишається основним джерелом для React. SSR читає той самий сервіс і ту саму ревізію.

Node перевіряє п'ять мов, базову структуру і заголовки ревізії. Перевірена відповідь кешується у пам'яті. Раз на 15 секунд Node надсилає CMS `If-None-Match`; 304 зберігає попередній каталог. Ревізія — `X-Content-Revision`, ETag — `"cms-<revision>"`. Клієнтські GET/HEAD підтримують 304. У HTML також передається заголовок ревізії.

Під час короткого збою допускається лише вже перевірена опублікована ревізія (`Warning: 110`). Коли CMS налаштована, холодна помилка, HTML замість JSON або неповний каталог дають 503, без підміни локальним файлом. Без `CMS_API_BASE_URL` лишається попередній локальний режим.

Публічний запис `POST /api/content` видалено: методи, крім GET/HEAD, повертають 405. Публікація виконується у PHP CMS.

`GET /api/content/media` проксіює метадані завантажень CMS. Відсутні записи для локальних `/imgs/...` не означають відсутності файлів; Node не вигадує для них розміри й не переносить їх до CMS.

## Preview

1. Адмінка відкриває `/?cms_preview=<48 hex символів>` або `/blog/preview/<id>?cms_preview=<token>`.
2. До канонізації URL Node перевіряє токен через CMS `/content/preview?token=...`.
3. Успіх створює ізольовану **15-хвилинну** сесію: випадковий ідентифікатор у `HttpOnly`, `SameSite=Lax` cookie; у production також `Secure`. Відповідь 303 прибирає токен з адреси.
4. Токен зберігається лише в пам'яті Node і не потрапляє до hydration JSON, canonical, партнерських посилань або JavaScript браузера. Перехід між внутрішніми сторінками працює через cookie.
5. Preview-запити звертаються до чернеток окремо від публічного кешу. `Cache-Control: private, no-store`, robots `noindex,nofollow,noarchive`, referrer `no-referrer`. Метадані чернетки не замінюють published snapshot.
6. CMS перевіряє строк свого токена при кожному запиті; її 403 не підміняється published-сторінкою. Локальна сесія завершується через 15 хвилин або перезапуск Node.
7. `POST /api/content/preview/end` завершує локальну сесію й видаляє cookie. Після цього перезавантажити сторінку.

Для кількох Node-процесів потрібна прив'язка запитів сесії до процесу або перенесення сховища preview-сесій у спільний серверний store. Опублікований кеш може залишатися окремим у кожного процесу з однаковою перевіркою ревізій.

Preview перевіряти через Node SSR (`localhost:5001` у локальному середовищі), а не через Vite на 5173: обмін токена виконує сервер, який формує HTML.

Чернетка блогу: маршрут сайту **`/blog/preview/:id`**, де ID містить латинські літери, цифри, `_` або `-`, до 100 символів. Серверний запит — `/blog/preview/{id}?token=...`; браузерний — `/api/blog/preview/{id}` без токена. Частково заповнена чернетка дозволена в preview; публічний валідатор статті залишається суворим.

## Погоджені рішення для PHP-розробника

- Заявки приймає **поточний Node-сервер**. Для `website_package` він знаходить видимий тариф у тій самій published-ревізії, бере з неї ціну, валюту й `billing_type`, ігноруючи клієнтську ціну для обраного пакета. Невідомий або прихований пакет відхиляється.
- Окремого `intent` у заявці немає; trial і demo ведуть на одну форму `#trial-request`.
- Для перегляду статті використовуємо `/blog/preview/:id`, як описано вище.
- Додатковий `schemaVersion` зараз не додаємо до узгодженого тіла: `{ua,cz,sk,en,pl}` лишається без обгортки. Несумісну зміну схеми слід погоджувати окремо; номер публікації передається заголовком.
- Для перейменованої статті Node перевіряє `/blog/redirects/{old-slug}` і повертає справжній 301 зі збереженням `lang`. `to` перевіряється як slug; довільний URL неможливий. 404 і 503 не змішуються.
- Три скриншоти прикладів сайтів не створюємо й не підміняємо білими картками. Наявний `site_2.png` є зображенням опису. До одержання реальних скриншотів CMS має залишати галерею неопублікованою згідно зі своєю валідацією.
- Приховані сторінки інтеграцій, політики та TecDoc дають 404 і вилучаються з меню, sitemap та llms. Прихована секція лише не відображається.
- HTML FAQ, відео й політики використовує один allowlist `shared/content-html.json`; дозволені тільки класи `faq-video-*` та `ql-(align|indent|size|direction)-*`. `_blank` отримує `noopener noreferrer`. SVG із CMS використовується як файл у `<img>`.

## Перевірка перед перемиканням production

Отримати від CMS реальні 200/304/403/404/503 з заголовками; перевірити всі мови, ID та перестановки списків, порожні/приховані значення, live-публікацію без rebuild, строк preview, 301 мовної статті, серверну ціну заявки й metadata медіа. Дозвіл власника на пакети Vortex та редактуру юридичних/цінових текстів не замінюється фактом інтеграції.

Локальні контрактні перевірки: `npm --prefix server test`. Збірка клієнта й SSR: `npm run build`.
