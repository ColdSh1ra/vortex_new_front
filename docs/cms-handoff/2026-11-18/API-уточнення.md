# Уточнення до API CMS та перенесення контенту Vortex

Дата знімка: **18 листопада 2026 року**. Мови контенту: **ua, cz, sk, en, pl**.

Документ доповнює передане [початкове ТЗ CMS](reference/CMS-original-spec.md) і чинний [контракт блогу](reference/blog-api-sashko.md). Він враховує поточний код нового сайту, сім сторінок інтеграцій, політику конфіденційності й підготовлений, але прихований блок пакетів Vortex.

**Переданий експорт — знімок поточного контенту та пропозиція доповненого контракту, а не відповідь уже перевіреного API.** Реальна адреса CMS, відповіді й заголовки PHP API ще мають бути надані та перевірені. Цей пакет не виконує підключення CMS і не підтверджує його завершення.

## 1. Що передаємо і що потрібно підтвердити спочатку

- `content.json` — зведений знімок із кореневими ключами п’яти мов; додаткові структури нижче позначені як запропоновані.
- Окремі мовні файли — ті самі дані для зручного імпорту й редактури; точні назви та порядок запуску експорту наведені в `README.md` цього пакета.
- `media-manifest.json` — посилання на публічні медіафайли й доступні фактичні метадані. Це інвентаризація для імпорту, **не** готова відповідь `GET /content/media`.
- `media-response.example.json` — окремий приклад погодженої обгортки `GET /content/media`, складений із фактичних оригіналів. `variants: []` означає, що WebP/thumb не згенеровані; похідні файли не вигадані.
- `export-report.json` — склад експорту, перевірки та знайдені прогалини. Відсутні файли й порожні поля потрібно виправити або погодити, а не замінювати вигаданим контентом.
- `raw-source/` — оригінальні джерела без зміни байтів, щоб перевірити адаптацію полів; архів і порядок відтворення описані в README. Публічний контент не включає налаштування доступу до адмінки, токени або приватні дані користувачів.
- `reference/demo-blog.json` — **лише демонстраційна довідка**: 20 summary і базова стаття п’ятьма мовами. Це не експорт реальних публікацій CMS і не матеріал для автоматичної публікації.

Пріоритетні відповіді від CMS-розробника:

| Пріоритет | Питання / потрібний результат |
| --- | --- |
| P0 | Надати реальні production і test API base URL замість `https://site-api.<домен>/api`, доступні Node-серверу без браузерної PHP-сесії. |
| P0 | Надати повний актуальний експорт `GET /content` усіма п’ятьма мовами, приклади 200/304/403/404/503 і фактичні `ETag`, `X-Content-Revision`, `Cache-Control`, `Retry-After`. |
| P0 | Підтвердити додавання `integration_pages`, `privacy_policy`, `seo.privacy_policy`, `seo.integrations[slug]`, `homepage.vortex_pricing_section`; цих структур немає в первісному описі CMS. |
| P0 | Підтвердити ізоляцію чернеток, строк дії та область дії токена, адресу перегляду статті й поведінку після завершення строку дії. |
| P0 | Імпортувати наявні тексти/медіа без втрати семи slug, реферальних query-параметрів, 14 розділів політики, явного складу тарифів. Пакети Vortex залишити прихованими й порожніми. |
| P1 | Узгодити поля періоду/валюти та тексти, що відрізняються між тарифами сайтів; структуровані комерційні умови TecDoc; перевірку ціни на сервері заявки. |
| P1 | Узгодити вкладене меню, сумісність старих якорів автошроту, семантику порожнього значення й приховування цілої сторінки. |
| P1 | Надати fixtures редиректів/preview блогу, медіатеки та приклади граничних станів для спільного приймання. |

Усі нові поля нижче потрібно підтвердити на стороні CMS або запропонувати еквівалентне відображення без втрат. Сам факт їх наявності в експорті не означає, що PHP API вже їх підтримує.

## 2. Чинний контракт і фактичний стан сайту

Зберігаємо описаний у вихідному ТЗ напрям: **PHP CMS → Node → SSR і React**. Публічний `GET /content` повертає об’єкт `{ ua, cz, sk, en, pl }` без додаткової обгортки; обгортку `{ data: ... }` використовують лише методи, де вона явно описана. Якщо фактичний PHP API має іншу форму, потрібна одна погоджена схема до підключення.

Параметри Node: `CMS_API_BASE_URL` і `BLOG_API_BASE_URL` — реальний корінь API **без кінцевого `/blog`**, `BLOG_DEMO_MODE=false`. Параметр збірки клієнта: `VITE_BLOG_DEMO_MODE=false`. Браузер звертається до same-origin Node `/api`; CMS URL і секрет preview не повинні ставати публічними build-time налаштуваннями. Публічні методи — GET без cookies/адмін-авторизації, `Accept: application/json`; відповідь — `application/json; charset=utf-8` зі справжнім HTTP-статусом.

| Шлях від API-кореня | Видача за ТЗ |
| --- | --- |
| `/content` | Повна опублікована ревізія п’ятьма мовами; `ETag`, `X-Content-Revision`. |
| `/content/preview?token=...` | Ізольована чернеткова ревізія тієї самої схеми. |
| `/content/media` | `{ data: { [url]: metadata } }`. |
| `/blog/posts`, `/blog/posts/{slug}`, `/blog/sitemap` | Чинний контракт блогу без змін. |
| `/blog/redirects/{slug}` | Запропонований redirect lookup, уточнення в розділі 9. |
| `/blog/preview/{id}?token=...` | Чернетка статті; маршрут перегляду сайту ще потрібно погодити. |

Помилки content API за вихідним ТЗ: `404 {"code":"NOT_FOUND"}`, `403 {"code":"PREVIEW_FORBIDDEN"}`, `503 {"code":"CONTENT_UNAVAILABLE"}` з `Retry-After: 60`; blog зберігає власні погоджені коди. Потрібні фактичні fixtures відповідей і заголовків, включно з **304 без тіла**, та підтвердження валідації неповної локалізації.

| Частина | Є зараз у новому сайті | Потрібно під час CMS-інтеграції |
| --- | --- | --- |
| Основний контент | Локальний `server/data/vortex.json`; спільний content service для Node/SSR/API. | Читання CMS, кеш ревізій, перевірка структури, остання справна копія. |
| Зміна контенту | Існує `POST /api/content`, що змінює локальний файл. | Видалити публічний запис; редагування лише через CMS. |
| Переклади | Частина UI та сторінок у `client/src/locales`; їх пріоритет може перекривати `content.ui`. | CMS має пріоритет; локальні тексти — тільки погоджений fallback відсутніх ключів. |
| Інтеграції / політика | Повні локальні тексти п’ятьма мовами й окремі маршрути вже реалізовані. | Перенести дані в CMS і підключити їх до тих самих сторінок, SSR та SEO. |
| Блог | Є проксі списку, статті й sitemap, валідація та справжні помилки. | Реальний API, вимкнення demo, нові redirect і preview; вони ще не підключені. |
| Preview CMS | Токенний перегляд і окремий draft-кеш не реалізовані. | Ізольований маршрут обробки до нормалізації публічного URL. |
| Тарифи сайтів | Три пакети та правила включення послуг у коді. | Дані CMS за стабільними ID, явна матриця, серверна перевірка пакета й ціни. |
| Пакети Vortex | Тип, верстка й точка підключення вже є; `visible: false`, `plans: []`. | Зберегти цей стан до погодження відповідальною особою; не наповнювати автоматично. |

Поведінку з вихідного ТЗ зберігаємо: довільна довжина масивів; `visible: false` приховує секцію; приховані записи списків CMS прибирає перед видачею; `href: null` документа СТО означає текст без посилання. Порожнє посилання месенджера не створює кнопку. Необов’язкові порожні поля блоків СТО опускаються, але кількість блоків не фіксується.

Зберегти плейсхолдери текстів на зразок `{number}` у `sync_section.client_label` і ключі `ui`; підстановка відбувається у визначених місцях, без виконання шаблонного коду з CMS. Для FAQ узгодити однакове очищення дозволених тегів і `ql-align-*`/`ql-indent-*` на CMS, SSR і клієнті; вузький поточний sanitizer не повинен тихо видалити погоджене форматування. Відеокартки зберігають `faq-video-grid`/`faq-video-link`, а не довільний iframe. Політика має окремий allowlist із `<code>` (розділ 5).

**Видалений блок `homepage.why_vortex_showcase_section` не відновлювати.** Він прибраний із проєкту за окремим рішенням користувача. Згадку у старому ТЗ слід вважати застарілою; старий ключ у CMS архівувати/ігнорувати, а не автоматично монтувати компонент.

## 3. Мови, маршрути, SEO та якорі

| Ключ JSON/API | HTML `lang` / hreflang | URL |
| --- | --- | --- |
| `ua` | `uk` | базовий маршрут без `lang` |
| `cz` | `cs` | `?lang=cz` |
| `sk` | `sk` | `?lang=sk` |
| `en` | `en` | `?lang=en` |
| `pl` | `pl` | `?lang=pl` |

Не перейменовувати `ua`/`cz` на `uk`/`cs` у JSON. Маршрути спільні для мов; перемикач мови зберігає поточну сторінку, підрозділ і пагінацію. Регістр чинних integration slug зберігаємо.

| Публічний маршрут | Ключ SEO в `content[lang].seo` |
| --- | --- |
| `/` | `home` |
| `/car-service` | `car_service` |
| `/websites` | `websites` |
| `/auto-dismantling` | `autoshrot` |
| `/tecdoc-license` | `tecdoc` |
| `/faq` | `faq` |
| `/contact` | `contacts` |
| `/blog` | `blog` |
| `/privacy-policy` | **`privacy_policy` — доповнення** |
| `/integrations/{slug}` | **`integrations[slug]` — доповнення**, усі сім slug нижче |
| `/blog/{slug}` | `data.translations[lang].seo` за чинним контрактом блогу |

Для нових SEO-ключів використовуємо той самий тип `{ title, description, share_image, share_image_alt, indexing: 'index' | 'noindex' }`. CMS керує змістом цих полів; canonical, hreflang, URL, breadcrumbs і JSON-LD формує сайт. Не імпортувати `title` сторінки як її маршрут. Повні SEO-дані мають бути у SSR HTML до запуску JavaScript і відповідати клієнтській версії.

Потрібно погодити: чи приховування сторінки означає 404, чи лише відсутність у меню? `visible: false` секції саме по собі не означає 404 для її окремої сторінки. Для `indexing: 'noindex'` передбачити robots і виключення відповідного URL із публічного sitemap. Публічні AI-довідники/`llms` також повинні будуватись із опублікованої ревізії, без чернеток і прихованих пакетів.

Чинні цілі навігації:

| Призначення | Ціль |
| --- | --- |
| Головні API-інтеграції | `/#integrations-catalog` |
| Облік СТО | `/car-service` або секція головної — зберігати конкретну ціль відповідного пункту експорту |
| Розробка сайтів | `/websites`, секція головної `/#website-development` |
| Ціни / калькулятор | `/#pricing` |
| Майбутні пакети Vortex | `/#vortex-plans`, тільки після дозволу на публікацію |
| FAQ / контакти / політика | `/faq`, `/contact`, `/privacy-policy` |
| Форма | `#trial-request`; службові цілі `form:trial`, `form:demo` |

Автошрот зараз використовує `dismantling-vehicle`, `dismantling-statuses`, `dismantling-parts`; новий контракт пропонує `hero`, `car`, `statuses`, `removal`, `workflow`. При переході додати сумісні aliases: `dismantling-vehicle → car`, `dismantling-statuses → statuses`, `dismantling-parts → removal`; створити точні ID для hero/workflow. Старі зовнішні посилання та поточні пункти меню не повинні перестати працювати. Фрагмент URL серверу не надходить, тому сумісність забезпечує сторінка.

Додаткові запропоновані поля автошроту в знімку: `navigation.label` для доступної назви навігації; `car.eyebrow`, `statuses.eyebrow`, `removal.eyebrow` для наявних підписів; `anchor_aliases` як явна карта сумісності. Поточні зображення автошроту декоративні, тому `image_alt: ""` тут свідомий стан, а не привід автоматично вигадати опис.

`layout.menu` у ТЗ плоский, а чинна навігація має групи. Пропозиція сумісного розширення: `{ id, label, target?: string, children?: MenuItem[] }`, де `children` необов’язкове; старі `{ id, label, target }` залишаються валідними. Потрібно підтвердити підтримку ієрархії, порядок і допустиму глибину, а не втратити підменю під час імпорту.

Для збереження фактичного вигляду експорт пропонує `layout.header_menu` з групою `children`, окремий `layout.footer_menu` у нинішньому порядку та необов’язковий `layout.socials[].icon`. Плоский `layout.menu` зберігається для сумісності; не показувати його одночасно з `header_menu` як друге меню. У `reference/presentation.json` зафіксовані контекстні цілі пункту цін: `/car-service#pricing` і `/websites#pricing` на відповідних сторінках, `/#pricing` на інших. Мовні параметри до внутрішніх цілей додає сайт.

`form:trial` і `form:demo` **зараз відкривають ту саму форму**, окремого `intent` у заявці немає. Потрібне рішення: залишаємо один сценарій чи додаємо погоджене поле наміру на frontend і backend. Не вважати новий payload уже реалізованим. Цілі переходу перевіряти за дозволеними форматами з ТЗ; не виконувати довільний JavaScript із CMS.

## 4. Сім сторінок інтеграцій — обов’язкове доповнення

Каталог `homepage.integrations_catalog_section` покриває лише вступ і картки. Його недостатньо для повних сторінок. Окремо переносимо всі тексти `client/src/locales/integrations/{lang}.json` та медіа з `client/src/data/apiIntegrations.ts`.

| Сервіс | Стабільний slug / маршрут | Кількість ілюстрацій у знімку |
| --- | --- | --- |
| TecDoc Inside | `tecdoc` → `/integrations/tecdoc` | 4 |
| Checkbox | `checkbox` → `/integrations/checkbox` | 2 |
| Вчасно.Каса | `vchasno` → `/integrations/vchasno` | 2 |
| Нова пошта | `nova_poshta` → `/integrations/nova_poshta` | 5 |
| TurboSMS | `turboSMS` → `/integrations/turboSMS` | 2 |
| Bank API | `bank_API` → `/integrations/bank_API` | 2 |
| Binotel | `binotel` → `/integrations/binotel` | 2 |

Не зводити `/integrations/tecdoc` до `/tecdoc-license`: це різні сторінки з різним призначенням. Зберегти логотипи з `/imgs/api-integrations`, усі **19** ілюстрацій із підпапки `screenshots`, реальні alt і прив’язку зображень до тексту. У Нової пошти перші дві ілюстрації належать першим двом розділам, третій розділ не має ілюстрації; решта три показуються галереєю. Не покладатися лише на індекс розділу як постійний зв’язок після редагування CMS.

Запропонований корінь — `content[lang].integration_pages`. Він містить `visible: true`, спільні підписи (`label`, `eyebrow`, `connect`, `viewFeatures`, `featuresTitle`, `linksTitle`, `back`, `relatedTitle`) і `pages[slug]`. Сторінка в експорті має таку форму:

```ts
{
  visible: boolean;
  slug: string;
  path: string;
  title: string;
  lead: string;
  logo: string;
  logo_alt: string;
  sections: {
    title: string;
    paragraphs: string[];
    items: string[];
    image: string;
    image_alt: string;
  }[];
  gallery: { image: string; alt: string }[];
  links: { label: string; href: string }[];
}
```

Під час імпорту потрібно зберегти:

- `title`, `lead` для hero;
- впорядковані `sections[]` із `title`, `paragraphs[]`, `items[]`;
- `links[]: { label, href }` для партнерських/реферальних переходів;
- логотип, набір ілюстрацій та відображення «розділ → зображення / галерея» без втрати наявних зв’язків;
- стабільні ID для майбутнього переставляння розділів і медіа; точний спосіб додавання ID погоджуємо перед API-адаптером.

Ця форма — основа для узгодження, а не вже впроваджене PHP API. Інші картки каталогу зв’язуємо з деталями через той самий стабільний slug; `link_href` веде на `/integrations/{slug}`. Функції на початку детальної сторінки беруться з відповідної картки каталогу, тому їх не можна загубити або підмінити іншим сервісом. Hero, breadcrumbs, список можливостей, усі текстові розділи, ілюстрації, партнерські посилання та інші інтеграції мають лишитися доступними.

Зберегти обидві пропозиції Вчасно.Каси, їхні п’ять перекладів і зв’язок кожного підпису з правильним URL. Не відкидати `utm_source` чи `registration_code` під час нормалізації. Це перенесення чинного знімка; актуальність комерційних умов перед публікацією підтверджує відповідальна особа.

## 5. Політика конфіденційності — окремий документ CMS

Маршрут **`/privacy-policy`**. Переносимо всі п’ять локалізацій, а не тільки текст footer-посилання. Запропонований корінь `content[lang].privacy_policy` містить `visible: true`, чинні `eyebrow`, `title`, `lead`, `updated` (локалізований підпис дати), `contents`, `sections[]: { id, title, html }` і машинну дату редакції **`updated_at: '2026-11-16'`**. Не підміняємо її датою експорту/перегляду.

У знімку **14 розділів**. Зберігаємо порядок, стабільні `id`, усі абзаци, списки, посилання і `<code>`; фронтенд утворює зміст і якорі `privacy-{id}`. Підтримуваний у поточній сторінці HTML: `p`, `ul`, `li`, `a`, `strong`, `code`, атрибути посилань `href`, `target`, `rel`. Застосовувати окремий погоджений sanitizer на CMS і frontend/SSR; довільний HTML, скрипти або inline-стилі не потрібні.

Юридичні реквізити, контакт `crm.vtx@gmail.com`, посилання, опис форми/геолокації/reCAPTCHA/cookie потрібно перенести без скорочень чи автоматичного переписування. Це знімок чинного тексту, а не нова юридична редакція. Майбутні зміни обробки даних і тексту політики погоджуються відповідальними особами окремо. SEO знаходиться в новому `seo.privacy_policy`.

## 6. Тарифи сайтів, TecDoc і приховані пакети Vortex

### 6.1. Сайти: три тарифи й усі 27 послуг

Знімок поточного коду: `free = 0`, `practical = 300`, `maximum = 500`, валюта **`USD`**. Для free — `billing_type: 'free'`, для practical/maximum — **`billing_type: 'one_time'`**: це вартість створення сайту, а не місячна ціна CRM. Для платних сайтів окремо переноситься локалізований текст **«+$10 на місяць за 10 тис. запитів»**, для безкоштовного — його чинна примітка. Не змінювати назви, суми, період чи обіцянки внаслідок технічного імпорту. Ці значення **не є новим погодженням комерційних умов**.

ТЗ має `billing_type: free | monthly | one_time`; експорт уже зберігає додаткову оплату в `extra_payments_note`. Якщо CMS має розраховувати й додаткову місячну оплату, потрібно погодити окремі структуровані суму, період і одиницю запитів; одного `price` недостатньо. Власна валюта/період тарифу не зобов’язані збігатися з калькулятором чи EUR ліцензії TecDoc. У поточному `settings.pricing_calculator.currency` усі п’ять мов мають **`"$"`**: зберігаємо це значення й не підміняємо його UAH під час експорту. ### 6.2. TecDoc

Чинний інтерфейс показує **25 EUR за ліцензію на місяць** і текст про **оплату на рік уперед**. Це не валюта калькулятора й не тариф розробки сайту. Схема `tecdoc` у ТЗ не має структурованих ціни й ліцензійного періоду. Експорт пропонує `tecdoc.license: { visible, eyebrow, price: 25, currency: 'EUR', billing_type: 'monthly', price_period, payment_terms, trial_terms, trial_badge }` із точними локалізованими умовами. Потрібно підтвердити цю форму й вирішити, чи річна передоплата, одиниця ліцензування й trial мають також окремі машинні поля. Не вгадувати іншу суму/строк і не парсити текст `25 €` для перевірки заявки. Це знімок, нові комерційні умови не вигадуємо.

Додаткові запропоновані поля TecDoc: `hero.secondary_cta_text`, `hero.secondary_cta_target`, `hero.details[]`; `sections[].eyebrow`, `sections[].blocks[]: { id, title, paragraphs[] }`. Вони зберігають другий CTA, бейджі та вкладені абзаци «Про TecDoc». Числові stats зберігають `+` та локалізовані суфікси мільйонів/тисяч. Hero зараз без зображення: порожнє поле не замінювати вигаданим. `tecdoc.cta` описує форму запиту, а не платіжний endpoint; `requested_product=tecdoc` зберігається.

Підґрунтя описане в [vortex-plans.md](reference/vortex-plans.md). Стан **усіх п’яти мов**:

  "section_description": "",
  "plans": []

Корінь — **`homepage.vortex_pricing_section`**. Нове поле заявки на зразок `vortex_plan_id` має бути погоджене окремо від `website_package`; optional callback у компоненті ще не є готовим API вибору CRM-пакета.

## 7. Медіа, галерея та незаповнений контент

Підтверджуємо вихідну вимогу: абсолютні HTTPS URL CMS і наявні `/imgs/...` підтримуються одночасно; відносну статику не прибирати до завершення міграції. API медіа — `{ data: { [url]: { width, height, mime, size, alt: { ua, cz, sk, en, pl }, variants: [...] } } }`; `variants` з `role: webp | thumb | original`. Потрібні реальні позитивні розміри та mime, а не оцінки. Для SVG — очищений файл у `<img>`, не довільне inline SVG з API.

Потрібно підтвердити синхронізацію ревізії контенту й медіатеки: новий контент не повинен посилатися на файл, якого ще немає; заміна медіа має новий URL і довгий кеш. Надати fixtures оригіналу/WebP/thumb, SVG, відсутнього файла й alt п’ятьма мовами. Не прибирати query-параметри партнерських посилань разом із нормалізацією медіа.

`websites.gallery` має замінити `import.meta.glob`: додавання файлу/картки в CMS повинно працювати без rebuild. У поточній папці сайтів немає повного набору очікуваних `overview`/`example-free`/`example-practical`/`example-maximum`; не видавати білу заглушку за готове портфоліо. Водночас наявний `site_2.png` використовується на головній через `homepage.website_development_section.website_image_src` — його не слід вважати відсутнім або автоматично призначати прикладом іншого тарифу. Саме CMS-поле має стати джерелом головного зображення `/websites`, замість окремого build-time glob. Для прикладів потрібні реальні файли, назви, alt, тип шаблону й ціль картки.

Наявні порожні поля, Lorem ipsum, чернеткові відгуки чи відсутні посилання відтворюються у знімку чесно й позначаються для редактури. Експорт не є дозволом публікувати вигадані відгуки, імена або непідтверджені результати. Остаточний перелік пропусків дивитися в `export-report.json` і `media-manifest.json`.

## 8. Кеш, публікація та безпечний preview

### Опублікований контент

1. Node отримує `/content`; одна перевірена ревізія використовується для SSR, hydration/`GET /api/content`, SEO та довідкових публічних ресурсів. Не змішувати дві ревізії в одному документі.
2. Кеш пам’яті перевіряється `If-None-Match` раз на погоджені 10–30 секунд. `304` не має нового JSON і **не обнуляє** кеш. `X-Content-Revision` — стабільний ідентифікатор публікації, не випадкове значення кожного GET.
3. Мережевий збій, 503, некоректний JSON або невалідна повна структура не замінюють робочий знімок. Є остання справна копія — віддаємо її; немає — 503 з доречною помилкою, не порожній 200.
4. Погодити межу застарівання/спостережуваність останньої справної копії та її поведінку після restart. Локальний JSON — лише окремо погоджений read-only аварійний резерв, не приховане основне джерело.
5. Публікація CMS оновлює всі п’ять мов атомарно; бажано погодити `schemaVersion`/політику сумісності. Числа й booleans повертаються числами й booleans; порожній список — `[]`, не `{}`.
6. Відсутній ключ, явний `""`, `null`, `false` і `0` не тотожні. Потрібно погодити валідацію обов’язкових полів і fallback лише відсутнього ключа. Локальний fallback не повинен знову показати приховану секцію, порожню кнопку чи іншу ціну.

### Попередній перегляд

Вихідне ТЗ визначає `?cms_preview=<token>` і CMS `/content/preview?token=<token>`; це потрібно реалізувати **окремо від публічного кешу**. Нині нормалізатор публічного URL прибирає сторонні параметри, включно з `cms_preview`, і може зробити 301 до втрати токена. Preview розпізнаємо до цього кроку; не змінюємо публічний canonical заради збереження секрету в ньому.

- Жодного fallback з чернетки в опублікований кеш чи навпаки; зміна чернетки не публікує її. Валідна preview-відповідь не перезаписує last-good public snapshot.
- SSR HTML, preview JSON і проксі відповіді — `Cache-Control: private, no-store`; без спільного CDN/public cache. Meta robots **`noindex, nofollow`**; погодити також відповідний `X-Robots-Tag`.
- Токен переноситься лише між внутрішніми preview-сторінками та мовами в погодженому механізмі. Його немає у canonical/hreflang, JSON-LD, sitemap, `llms`, публічному експорті та зовнішніх партнерських посиланнях.
- Пропозиція безпечнішої реалізації: обміняти токен на ізольовану коротку HttpOnly preview-сесію й прибрати його з адреси. Це **потребує погодження**, не змінює самовільно описаний query-протокол. У будь-якому варіанті прибрати токен з логів/аналітики й не передавати його стороннім ресурсам через referrer; погодити scope, завершення сесії та invalidation.
- Строк токена за ТЗ — одна година. `403 PREVIEW_FORBIDDEN` показує зрозуміле повідомлення про застаріле/недійсне посилання, не опубліковану сторінку під виглядом preview. Потрібна точна схема генерації посилань і приклади чинного/простроченого токена через безпечний канал.

## 9. Блог: зберегти старий контракт, уточнити два нові сценарії

Базовий [blog-api-sashko.md](reference/blog-api-sashko.md) не переписуємо: `GET /blog/posts?page=1&limit=16`, `/blog/posts/{slug}`, `/blog/sitemap?page=1&limit=1000`; усі п’ять перекладів за один запит, стабільні ID/slug, plain-text sections, ISO UTC дати, фактичні HTTP статуси, повний SSR і sitemap. UI-тексти переносяться в `blog_copy` зі збереженням ключів `blog/copy.ts`.

`seo.blog.indexing: "index"` у `content.json` — запропоноване значення для майбутнього live-блогу, а не зняття чинного demo/noindex. Поточне правило `noindex,follow` для demo має окремий пріоритет незалежно від цього поля.

В обох production-параметрах demo має бути вимкнене: `BLOG_DEMO_MODE=false` та `VITE_BLOG_DEMO_MODE=false`. Не підміняти справжню помилку демонстраційною статтею. PHP має повертати JSON, а не HTML login/warning. Для браузера лишається same-origin Node `/api/blog`; окремий CORS до PHP не потрібен.

Демонстраційні записи з `reference/demo-blog.json` залишаються окремою довідкою, не автоматичним seed публічного блогу. Чинний demo/noindex-стан SEO потрібно перенести чесно як поточний знімок, а не прибирати його лише тому, що готується CMS-експорт. Публічне індексування production-блогу вмикаємо після підключення реальних даних і приймання відповідних умов.

**Редиректи:** ТЗ пропонує на 404 статті запитати `/blog/redirects/{old-slug}` → `{ data: { from, to } }`, після чого Node віддає справжній 301 на `/blog/{to}` зі збереженням мови. Потрібно підтвердити, що `to` — slug, не довільний URL, і відповісти:

- Який статус/код, коли редиректу немає? Як відрізняємо це від тимчасової недоступності сервісу?
- Чи одразу повертається кінцевий slug? Як виключаємо цикли, ланцюги й перенаправлення на приховану/видалену статтю?
- Як змінюються canonical і sitemap після перейменування, що зі старими якорями? Потрібні fixtures, включно зі збереженням `?lang=...`.

**Чернетка статті:** `/blog/preview/{id}?token=...` описує API, але ще не визначає публічний маршрут сайту. Потрібно погодити preview URL, допустимий ID/slug, формат `{ data: Post }` чи інший, область токена, режим частково перекладеної чернетки та 403/404. Не відкривати чернетку через публічний `/blog/posts/{slug}`, список чи sitemap. Ізоляція, `no-store` і `noindex, nofollow` такі самі, як для загального CMS-preview.

## 10. Останні зміни дизайну: зберегти при підключенні CMS

Це правила презентації, які залишаються у React/CSS. Їх не потрібно перетворювати на довільні CSS-поля, координати чи JavaScript у CMS:

- **Vortex Sync:** по п’ять шляхів у кожному напрямку, 20 маленьких рухомих кружків; колір кружка відповідає помаранчевому/білому шляху. Рухомих іконок немає. Тривалість початкової анімації збережена; геометрія, швидкість, reduced-motion та пауза поза екраном — код клієнта. CMS редагує лише передбачені тексти, підписи й контентні зображення.
- **Помаранчеві CTA:** прозорий `double-chevron-right.svg`; світло-жовте коло створює HTML `div`, а не фон SVG. Єдина логіка для всіх помаранчевих кнопок, включно з картками, СТО й розробкою сайтів.

## 11. Поділ робіт і приймання

**CMS/PHP:** імпортувати всі мови; підтримати погоджені доповнення схем; повернути fixtures і реальний API; редагування/публікація/preview; цілісність медіа, реферальних URL, ID та матриць; валідація й HTML sanitation на вході/виході. Бізнес-власник підтверджує ціни, умови, реферальні пропозиції, юридичні правки й дозвіл на публікацію пакетів Vortex.

**Node/React:** адаптер CMS і перевірка відповіді; спільна ревізія SSR/клієнта; ETag/304/LKG; видалення локального POST; пріоритет CMS над локалями; адаптація вже наявних сторінок/галереї/тарифів; динамічні SEO/sitemap/довідники; redirects; ізольований preview; безпечні переходи та узгоджена серверна перевірка заявки. Фіксовані макетні й анімаційні правила залишаються тут.
